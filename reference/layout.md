# วางการ์ด: เลือกเนื้อหาและลำดับ (ทาง ENGINE)

ไฟล์นี้คือการเลือก section ของ CONFIG ในแม่แบบ ENGINE · หน้าออกแบบเอง (ทางที่ 2) ใช้ brief ข้อ 1, 3, 4 ของไฟล์นี้เหมือนกัน แต่เลือกชิ้นส่วนและการจัดเรียงตาม `design.md` (หน้าตาเป็นธีมเดียวกัน)

ทำ **brief** ก่อนแตะ CONFIG แล้วให้ทุกการ์ดชี้กลับไปที่คำถามข้อใดข้อหนึ่งใน brief ได้ การ์ดที่ตอบคำถามไหนไม่ได้ให้ตัดทิ้ง
หน้าตาเหมือนกันทุกโปรเจกต์ แต่**เนื้อหาต้องมาจากข้อมูลและคนอ่านของโปรเจกต์นั้น** ห้ามยกการ์ดของ preset chatbot (โควตา, session, คีย์เวิร์ด, คุณภาพคำตอบ) ไปใส่ข้อมูลชนิดอื่น

## brief (เขียนก่อน)

1. **คนอ่าน** และเปิดหน้านี้เพื่อตัดสินใจเรื่องอะไร
2. **หนึ่งแถวคืออะไร** (คำถาม / คำสั่งซื้อ / ticket / คำขอ / รอบการรัน / งาน) คำนามนี้คือ `unit` และ**แถวไหนเป็นแถวทดสอบหรือแถวเสีย** (ไม่มีรหัส, ลูกค้าทดสอบ, session ที่ไม่ใช่ UUID) ซึ่งจะกลายเป็น `keep`
   และมีเวลาที่สองไหม (เวลาปิด ชำระ หรือเสร็จ) ถ้ามี กราฟนับตามเวลานั้นได้ด้วย `trend.metrics[].at`
3. **คำถาม 3–5 ข้อ เรียงตามความสำคัญ** เช่น "ตอนนี้ระบบปกติไหม" มาก่อน "ใครใช้มากสุด"
   แต่ละข้อถามถึง **"ตอนนี้"** (งานค้าง ticket ที่เปิดอยู่ ใช้ `ctx.all` / `allTime`) หรือ **"ในช่วงที่เลือก"** (ค่าเริ่มต้น)
4. **ตัวเลขที่มีเกณฑ์** เช่น เพดาน เป้า SLA หรืออัตราผิดพลาดที่ยอมรับได้ พร้อมนิยามที่ชัด (เช่น SLA นับเวลาทำการหรือนับ 24 ชม.) ถ้าไม่มี ห้ามสร้างขึ้นเอง
5. **ลิงก์กลับระบบต้นทาง** (URL ของ ticket หรือ execution) ถ้ามี ให้ใส่ใน detail
6. **ที่รัน** (ดู `serving.md`): VPS หลัง nginx login, ฝังในแอปเดิม หรือในเครื่องคนเดียว

## ลำดับบนหน้า (บนลงล่าง = ด่วนไปถึงละเอียด)

| ลำดับ | section | ตอบคำถามแบบไหน |
|---|---|---|
| 1 | `kpis` | ตอนนี้เป็นอย่างไร ปกติไหม ถึงเกณฑ์ไหม |
| 2 | `trend` | เปลี่ยนไปอย่างไรตามเวลา |
| 3 | `breakdown` | แบ่งตามผลลัพธ์หรือสถานะแล้วเป็นสัดส่วนเท่าไร (ค่าเริ่มต้นวางข้างกราฟ) |
| 4 | `rankings` | ใครหรืออะไรมากที่สุด |
| 5 | `table` | รายการจริงทีละแถว ค้นหาและส่งออกได้ |
| – | `detail` | อ่านทั้งระเบียนหรือทั้งกลุ่ม (เมนูแยก) |

ค่าเริ่มต้นคือ `layout: ['kpis', 'trend', 'rankings', 'table']` ให้เปลี่ยนลำดับเมื่อ brief บอกว่าคนอ่านมาเพื่อดูรายการเป็นหลัก เช่น หน้าที่หัวหน้าเปิดทุกเช้าเพื่อไล่ ticket ค้าง ให้ใช้ `['kpis', 'table', 'trend', 'rankings']`
section ไหนไม่ได้ตอบคำถามใน brief ให้เอาออกจาก `layout` ส่วน `kpis` กับ `table` มีเสมอ
ถ้าใส่ `'breakdown'` ใน `layout` มันจะแยกออกมาเป็นแถวของตัวเอง ณ ตำแหน่งนั้น

## KPI (2–4 ใบ เรียงซ้ายไปขวาตามความสำคัญ)

- **ใบแรกตอบคำถามข้อ 1 ของ brief** เช่น สุขภาพระบบ งานค้าง หรือความคืบหน้าเทียบเป้า ไม่ใช่ "จำนวนแถวทั้งหมด"
- ทุกใบเขียนเป็น **ป้าย + ตัวเลขเดียว + hint**
  - ป้ายบอกคำนามและช่วงเวลา ใช้ `ctx.label('งาน')` หรือ `` `Output tokens ${ctx.rangeName}` ``
  - ตัวเลขยาวไม่เกินประมาณ 9 ตัวอักษร ถ้ายาวกว่านั้นใช้ `fmtCompact` แล้วใส่ตัวเลขเต็มไว้ใน hint
  - hint ให้บริบทที่ทำให้ตัวเลขมีความหมาย เช่น ตัวหาร ค่าเทียบ หรือสิ่งที่ไม่นับ (`ผิดพลาด 12 จาก 340 ครั้ง`)
- **อัตรา (%)** ให้ใส่จำนวนจริงใน hint เสมอ เพราะ 50% จาก 2 ครั้งกับจาก 2,000 ครั้งไม่เหมือนกัน
- **ตัวเลขสถานะปัจจุบัน** (งานค้าง ticket ที่ยังเปิด) ไม่ขึ้นกับช่วงที่เลือก ให้คำนวณจาก `ctx.all` (อายุ/รอนานเท่าไรใช้ `ctx.now`) แล้วเขียนในป้ายว่า "ตอนนี้"
- **ตัวเลขที่มีเกณฑ์** ให้ใส่ `status: { tone, text }` ตามเกณฑ์ใน brief: `ok` = ผ่านเป้า, `warn` = ต่ำกว่าเป้า, `crit` = มีของที่ต้องลงมือตอนนี้หรือหลุดเส้นที่ตกลงว่าวิกฤต, `''` (สีกลาง) = ข้อมูลยังน้อยเกินตัดสิน ส่วน `meter` ใช้กับเพดานหรือเป้ารายเดือนเท่านั้น ถ้าไม่มีเกณฑ์ ให้ตัดการ์ดเดือนนี้ออก (ปุ่มช่วง "เดือนนี้" ให้คำตอบนั้นอยู่แล้ว)
- **ตัวเลขที่ต้องลงมือต่อ** (เกิน SLA 4 ใบ, 5xx 12 ครั้ง) ให้ใส่ `go: { filter, text }` ด้วยเงื่อนไขเดียวกับที่ใช้นับ (ไม่ใช่ค้นข้อความ) ถ้าเป็นตัวเลข "ตอนนี้" ให้ใส่ `allTime: true` ด้วย จำนวนแถวที่เปิดได้จะตรงกับตัวเลขบนการ์ด
- **อัตราเทียบเกณฑ์** (SLA %, อัตราผิดพลาด) เขียนกติกาการนับลงใน hint ให้ชัด: ตัวที่ยังไม่ครบเวลาเกณฑ์ไม่นับในตัวหาร ส่วนตัวที่ปิดไปโดยไม่ได้ตอบนับเป็นไม่ผ่าน ถ้า brief มีเกณฑ์ต่อชิ้นแต่ไม่มีเป้า % ให้ใส่ `status` ที่การ์ดจำนวนที่เกินเกณฑ์ ไม่ต้องใส่ที่การ์ด %
- **`status` ต้องมีขนาดตัวอย่างขั้นต่ำ** ที่ตกลงไว้ใน brief ถ้าน้อยกว่านั้นให้ขึ้น "ข้อมูลน้อย" (tone ว่าง) แทนปกติ/ผิดปกติ เพราะ 5xx หนึ่งครั้งจาก 17 คำขอคือ 5.9% และ p95 ของ 20 แถวคือแถวที่ช้าสุดแถวเดียว
  - ระบบที่มีปริมาณน้อย (หลักสิบต่อวัน) จะไม่ถึงขั้นต่ำเกือบตลอดเวลา จึงให้ตัดสินจาก**จำนวน**แทนอัตรา เช่น "5xx ตั้งแต่ 3 ครั้งใน 24 ชม. = ผิดปกติ" และบอกเกณฑ์ใน hint
- **กติกาสุขภาพที่มีหลายเงื่อนไข** (5xx < 2% **และ** p95 < 8,000 ms) ให้รวมเป็นการ์ดเดียว: value = ตัวเลขที่สำคัญที่สุด, `status` = ผลรวมของทุกเงื่อนไข, hint = ตัวเลขของทุกเงื่อนไขพร้อมเกณฑ์ (อย่าแยกเป็นสองการ์ดที่ไม่มีคำตัดสินรวม)
- **อายุ/รอนานเท่าไร/24 ชม. ล่าสุด** คำนวณจาก `ctx.now` (หรือ `Date.now()` ใน `cell` ของตาราง) ได้ ส่วน "วันนี้/เดือนนี้" ต้องใช้ `day` / `today` ของ engine และให้ป้ายบอกหน้าต่างเวลาให้ชัด (การ์ด 24 ชม. กับแท่งรายวันจะไม่เท่ากัน)
- การ์ดสองใบต้องไม่ตอบคำถามเดียวกัน และมีได้ไม่เกิน 4 ใบ ตัวเลขรองให้ไปอยู่ใน hint

## กราฟ (`trend`)

- ค่าเริ่มต้นนับแถว ถ้าคนอ่านติดตามผลรวม (ยอดเงิน token เวลา) ให้ใส่ `value` และ `unit`
- คนอ่านติดตามมากกว่าหนึ่งตัวเลข ให้ใช้ `metrics` (ปุ่มสลับ) **ห้ามวาดสองหน่วยบนแกนเดียว**
- อัตราต่อช่วง (อัตราผิดพลาดรายวัน) ใช้ `agg: rows => …` ของ metric · ของที่เกิดตามเวลาที่สอง (ticket ที่ปิด, เงินที่เข้า) ใช้ `at: l => l.closedAt`
  ```js
  trend: { metrics: [
    { key: 'req', label: 'จำนวนคำขอ', unit: 'คำขอ' },
    { key: 'err', label: 'คำขอที่ผิดพลาด', unit: 'คำขอ', value: l => l.status >= 500 ? 1 : 0 },
    { key: 'tok', label: 'AI tokens', unit: 'tokens', value: l => l.tokens, fmt: fmtCompact },
    { key: 'rate', label: 'อัตราผิดพลาด', unit: '%', agg: rs => Math.round(rs.filter(l => l.status >= 500).length / rs.length * 1000) / 10 },
  ] }
  ```

## สัดส่วน (`breakdown`)

- ใช้มิติเดียวที่**ปิด**และ**ไม่ซ้อนกัน** และบอกผลลัพธ์หรือสถานะ เช่น สถานะ ticket, ผลของคำขอ (สำเร็จ / 4xx / 5xx), ประเภทงาน หรือคุณภาพคำตอบ
- มีได้ไม่เกิน 5 กลุ่ม เรียงตามลำดับการไหลของงาน หรือจากดีไปแย่
- มิติ**เปิด** เช่น ลูกค้า คน ฟีเจอร์ หรือสินค้า ให้ใช้ `rankings` แทน
- กดกลุ่มแล้วตารางกรองตาม และ dropdown ของตารางใช้มิตินี้ จึงควรเลือกมิติที่คนอ่านอยากกรองจริง
- สัดส่วนของ "สถานะตอนนี้" (ticket เปิด/รอ/ปิด) ให้ใส่ `allTime: true` ไม่งั้นจะเห็นแค่ ticket ที่เปิดในช่วงที่เลือก

## อันดับ (`rankings`)

- ใช้กับมิติเปิด แสดงสองใบต่อแถว เรียงตามความสำคัญใน brief
- บอกใน `cap` ว่าตัวเลขคือ**จำนวนแถว** **ผลรวม** หรือ**อัตรา**ของอะไร ผลรวมใช้ `value` ส่วนอัตรา ค่าเฉลี่ย หรือมัธยฐานต่อกลุ่มใช้ `agg` + `min` (กันกลุ่มที่มี 1–2 แถวขึ้นอันดับ)
- อันดับของ "ตอนนี้" (ภาระงานค้างต่อคน) ใส่ `allTime: true` · ถ้าคนอ่านอยากกดดูรายการของคนนั้น/สิ่งนั้น ใส่ `go: true`
- ถ้าต้องการรู้สิ่งที่แย่ที่สุด เช่น endpoint ที่ผิดพลาดบ่อยหรือลูกค้าที่ ticket ค้างมากสุด ให้ `keys` คืน `null` สำหรับแถวที่ไม่เกี่ยว (engine ข้ามให้) เช่น `keys: l => l.status >= 500 ? l.endpoint : null` อย่าเปลี่ยน `counted` เพื่อการ์ดใบเดียว เพราะ `counted` ใช้ร่วมกับ KPI และกราฟ

## ตาราง (`table`)

- หนึ่งแถวของตาราง = `unit` และคอลัมน์ "เวลา" อยู่แรกเสมอ
- มีคอลัมน์ของ config ไม่เกิน 5 คอลัมน์ ตามลำดับ: **อะไร** (`cls: 'main'` ใส่ `tagsHtml`), **ใคร/ที่ไหน**, **ตัวเลขหลัก**, **สถานะ/ระยะเวลา**
- `tags` ใช้กับ**ข้อยกเว้น**เท่านั้น เช่น ผิดพลาด เกิน SLA ส่งต่อ หรือหยุดกลางคัน ไม่ใช่ป้ายของทุกแถว (คำในป้ายค้นหาได้ จึงใช้แทนตัวกรองที่สองได้)
- หน้าที่ใช้ไล่งานค้าง ให้ตั้ง `sort` ตาม "ต้องลงมือก่อน" แล้วค่อยเก่าสุด เช่น `(a, b) => urgency(b) - urgency(a) || a.ms - b.ms` (เรียงแค่เก่าสุดก่อน ของที่เกิน SLA จะตกไปหน้า 2)

## หน้ารายละเอียด (`detail`)

ใส่เมื่อคนอ่านต้องอ่านของทั้งชิ้น ถ้าตารางพอแล้วให้ตั้ง `detail: null`

| ข้อมูล | กลุ่ม (`key`) | `render` |
|---|---|---|
| บทสนทนา (แชทบอท) | session | `turnEl` ของ preset chatbot (บับเบิลคำถาม-คำตอบ) |
| ระเบียนเดี่ยว (ticket, คำสั่งซื้อ, คำขอ) | ตัวระเบียน (key ไม่ซ้ำได้) หรือเจ้าของ (ลูกค้า, ผู้ใช้) + `order: 'newest'` | `recordHtml({ title, sub, tags, fields, body })` และ `openIcon: 'right'` |
| งานหลายขั้น (job run, session ของ agent) | งาน/session | `recordHtml` ต่อขั้น หรือ `timelineHtml([...])` |

## แจ้งเตือน (`notifs`)

แจ้งได้สามแบบ: (1) แถวใหม่ตั้งแต่เปิดดูครั้งก่อน (2) สถานะที่ค้างหรือเกินกำหนด เช่น ticket เปิดเกิน SLA หรือ 5xx ใน 1 ชั่วโมง (3) เกณฑ์ที่ถูกข้าม
แบบ (2) และ (3) ต้องมี `key` เพื่อไม่ให้เตือนซ้ำ และใส่ `go: { filter, text }` ที่เปิดรายการชุดนั้นตรงตัว โดย `filter` ใช้เงื่อนไขเดียวกับที่นับในแจ้งเตือน (รวม `l.ms > n.since` ถ้าแจ้งเฉพาะของใหม่) โดยให้ key เปลี่ยนเมื่อ**ชุดของ**เปลี่ยน เช่น `` `sla-${ids.join(',')}` `` ไม่ใช่แค่จำนวน (ใบหนึ่งหายอีกใบเข้ามา จำนวนเท่าเดิมแต่เป็นของใหม่)
ห้ามใส่แจ้งเตือนที่ไม่มีอะไรให้คนอ่านทำต่อ
