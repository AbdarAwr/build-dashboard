# สูตรตั้งต้นตามชนิดระบบ

แต่ละสูตรคือ**รายการให้เลือก ไม่ใช่ต้องใส่ครบ** เลือกเฉพาะที่ตอบคำถามใน brief (`layout.md`) แล้วเพิ่มสิ่งที่คำถามต้องการแต่สูตรไม่มี
โค้ดตั้งต้นคือ preset `generic` ของแม่แบบ (แชทบอทมี preset ของตัวเอง) ยกเว้นสูตรที่หัวข้อเขียนว่า "หน้าออกแบบเอง" ซึ่งเริ่มจาก `design/page.html`

## แชทบอท (log คำถาม-คำตอบ)
ใช้ preset `chatbot` ตามที่มี และอ่าน `chatbot-data.md` · หนึ่งแถว = คำถามหนึ่งข้อ · detail = บทสนทนาต่อ session

## ยอดขาย / คำสั่งซื้อ
preset `generic` คือสูตรนี้อยู่แล้ว (เป้าเดือน, ยอดขาย, จำนวน, สถานะ, สินค้าขายดี, ช่องทาง, ประวัติลูกค้าแบบระเบียน)

## ticket ซัพพอร์ต (หนึ่งแถว = ticket)
- **keep:** ตัดแถวที่ไม่มี ticket_id และ ticket ทดสอบ (ถาม user ว่ามีลูกค้า/แท็กทดสอบไหม)
- **KPI:** (1) ticket ค้างตอนนี้ (`ctx.all` สถานะ open/waiting, hint: ด่วนกี่ใบ ค้างนานสุดกี่วัน จาก `ctx.now`) (2) ยังไม่ตอบเกิน SLA ตอนนี้ (`status` crit เมื่อ > 0, `go` ไปรายการนั้น) (3) ตอบครั้งแรกทันเกณฑ์ในช่วง (% + `status` ตามเป้า, hint: ผ่านกี่ใบจากกี่ใบ ค่ามัธยฐานกี่นาที) (4) ticket ใหม่ในช่วง (hint: ปิดได้กี่ใบ)
- **trend:** `metrics` = ticket ใหม่ (เวลาเปิด) / ticket ที่ปิด (`at: l => l.resolvedAt`) / SLA % (`agg`, `min: 5`, `peak: 'min'`, `ref` = เป้า)
- **breakdown:** สถานะ (open → waiting → solved → closed) `allTime: true` **ไม่ใช่**ระดับความสำคัญ (priority ใช้เป็น tag ของ urgent/high)
- **rankings:** ภาระค้างต่อเจ้าหน้าที่ (`allTime`, `keys: l => open(l) ? l.agent : null`, `go`) · ลูกค้าที่มี ticket ค้าง (`allTime`, `go`) · ลูกค้าที่เปิด ticket มากสุดในช่วง · SLA % ต่อเจ้าหน้าที่ (`agg` + `min: 5`)
- **table:** หัวข้อ (+tag เกิน SLA / urgent) · ลูกค้า · เจ้าหน้าที่ · ตอบครั้งแรก (นาที) · สถานะ · `layout: ['kpis', 'table', 'trend', 'rankings']` และ `sort` เกิน SLA/ด่วนก่อน แล้วค่อยเก่าสุด ถ้าหัวหน้าเปิดมาไล่งานค้าง
- **detail:** กลุ่ม = ticket (`key: l => l.ticket_id` ไม่ซ้ำได้, `groupSort` ให้ที่เกิน SLA ขึ้นก่อน) render ด้วย `recordHtml` (fields: ลูกค้า, เจ้าหน้าที่, ความสำคัญ, เปิดเมื่อ, ตอบครั้งแรก, ปิดเมื่อ, ป้าย + ลิงก์กลับระบบต้นทาง) · ชื่อคอลัมน์ `tags` ของต้นทางให้เปลี่ยนเป็น `labels` ใน `toRow` (ชื่อสงวน)
- **notifs:** ticket ใหม่ · ticket ที่ยังไม่ตอบเกิน SLA (`key` = รายการ ticket_id ที่เกิน)
- **SLA %:** ตัวหาร = ticket ที่ตอบแล้ว + ticket ที่ยังไม่ตอบแต่เกินเวลาแล้ว (ตัวที่ยังไม่ครบ 60 นาทีไม่นับ) เขียนกติกานี้ใน hint

## log คำขอของแอป / API (หนึ่งแถว = คำขอ)
- **KPI:** (1) สุขภาพตามหน้าต่างเวลาใน brief เช่น 24 ชม. ล่าสุด (`ctx.all` + `ctx.now`) เป็นการ์ดเดียว: value = อัตรา 5xx, `status` = รวมทุกเงื่อนไข (5xx และ p95), hint = 5xx กี่ครั้งจากกี่คำขอ · p95 กี่ ms, `go` ไป 5xx ในหน้าต่างนั้น (2) เวลาตอบ p95 (หน้าต่างเดียวกับข้อ 1 ถ้า brief ถามว่า "ตอนนี้") (3) จำนวนคำขอในช่วง (hint: ผู้ใช้กี่คน ล้มกี่ครั้ง) (4) ต้นทุน เช่น AI tokens ถ้ามี (ใช้ `fmtCompact`)
- **trend:** `metrics` = คำขอ / ผิดพลาด / อัตราผิดพลาด (`agg`) / tokens
- **กรองคำขอของหน้า dashboard เอง** (หน้าโพลข้อมูลทุก N นาที) ออกใน `keep` ไม่งั้นจะนับรวมเป็นการใช้งาน
- **ถามให้ชัดใน brief:** คำขอแบบไหนนับว่า "ช้า" (ต่อคำขอ ไม่ใช่ p95), p95 รวมคำขอที่ error/timeout ไหม, endpoint ของ dashboard เองคืออะไร
- **breakdown:** ผลของคำขอ: สำเร็จ (2xx/3xx) · ผู้ใช้ส่งผิด (4xx) · ระบบผิดพลาด (5xx) · ช้าเกินเกณฑ์ (สำเร็จแต่ช้า) — ตัดสินตามลำดับ 5xx > 4xx > ช้า > สำเร็จ
- **rankings:** การใช้ตามฟีเจอร์ (`go`) · ตามผู้ใช้ (`go`) · อัตราผิดพลาดต่อฟีเจอร์ (`agg` + `min`) · p95 ต่อ endpoint (`agg`)
- **table:** endpoint/ฟีเจอร์ (+tag 5xx/ช้า) · ผู้ใช้ · status · ms · ข้อความ error (`cls: 'a'`) — ถ้าคนอ่านอยากเห็น error ให้ใช้ช่องนี้แทน tokens · `sort` ให้ที่ล้มขึ้นก่อน
- **trend p95 / ms:** ใส่ `max` (เช่น 3 เท่าของเกณฑ์) และ `ref` = เกณฑ์ ไม่งั้น timeout ครั้งเดียวทำให้เส้นเกณฑ์แบนติดพื้น
- **detail:** มักไม่จำเป็น (`null`) ยกเว้นต้องอ่านข้อความ error ยาว ๆ: กลุ่ม = ฟีเจอร์ หรือ endpoint, `order: 'newest'`, `recordHtml` โดยมี `body` = error message (`esc` แล้วห่อ `<pre>`)
- **notifs:** 5xx ใหม่ตั้งแต่เปิดดูครั้งก่อน · อัตราผิดพลาดวันนี้เกินเกณฑ์ (`key` = วัน)

## รอบการรันของงานตั้งเวลา (n8n / cron / ETL) — หนึ่งแถว = หนึ่งรอบ
- **KPI:** (1) รอบที่ล้มในช่วง (hint: workflow ไหน) (2) รอบล่าสุดของงานสำคัญ (สถานะ + เวลา, คำนวณจาก `ctx.all`) (3) จำนวนรอบ (4) เวลารันเฉลี่ย
- **breakdown:** success / error / canceled · **rankings:** workflow ที่ล้มบ่อย · ใช้เวลานานสุด
- **detail:** กลุ่ม = workflow, render = `timelineHtml` ของรอบ (tone ok/crit ตามผล)
- **notifs:** รอบที่ล้มใหม่ · งานที่ควรรันแต่ไม่รัน (คำนวณจากตารางเวลา ต้องมี `key`)

## งานของ AI agent (หนึ่งแถว = คำสั่งหนึ่งครั้ง + ทุกอย่างที่ agent ทำจนถึงคำสั่งถัดไป)
ตัวอย่างจริง: หน้าออกแบบเองที่รวมงานของ Claude Code + ระบบที่ deploy + งานตั้งเวลาไว้ในหน้าเดียว (ที่อยู่ใน `local/team-notes.md`)
- **KPI:** งาน (hint: กี่ session) · การเรียกใช้เครื่องมือ (hint: ผิดพลาดกี่ % ) · output tokens (`fmtCompact` + ตัวเต็มใน hint)
- **breakdown:** ประเภทงานตามเครื่องมือที่ใช้ (แก้ไฟล์ > รันคำสั่ง > ค้น/อ่าน > ตอบอย่างเดียว)
- **rankings:** โฟลเดอร์ · เครื่องมือ · session ที่ใช้ tokens มากสุด · ไฟล์ที่แก้บ่อย
- **detail:** กลุ่ม = session, render = คำสั่ง → เครื่องมือ/ไฟล์ → คำตอบสุดท้าย (โครง `turnEl` ใช้ได้ เพราะเป็นบทสนทนาจริง)

## บอร์ดสถานะ (ระบบ/บอท/สาขา N ตัว ณ ตอนนี้) — หน้าออกแบบเอง
- หนึ่งการ์ดต่อหนึ่งตัว (`UI.statCard` ใน `.grid`) **ลำดับคงที่ตามข้อมูล** ไม่เรียงใหม่ตามความรุนแรง คนดูจำตำแหน่งได้
- ตัวที่มีปัญหาทั้งใบเปลี่ยนสี (`state: 'crit'`/`'warn'`) ตัวที่ปกติเงียบ · สถานะที่ไม่รู้จักใช้ `'unknown'` ห้ามเดาว่าปกติ
- คำสรุปจำนวนแต่ละสถานะ (`.chips`) ไว้บนสุด และซ่อนเมื่อ `stale` · ตัวเลขที่ไม่มีเกณฑ์แสดงเป็นตัวเลขเฉย ๆ ไม่ใส่สี
- ถามให้ชัด: อะไรทำให้เป็น "ติดขัด", ตัวเลขแต่ละตัวนับช่วงไหน (วันนี้ตามเวลาไทย? 15 นาทีล่าสุด?), มีเกณฑ์ (SLA) ไหม, หลังบ้านส่ง `generated_at` ได้ไหม

## สรุปสำหรับผู้บริหาร (ยอดเทียบเป้า) — หน้าออกแบบเอง
- คำถามหลักมักเป็น "เดือนนี้" ไม่ใช่ช่วงที่เลือก จึงไม่มีตัวกรองช่วงทั้งหน้า ไม่มีตารางรายการ ไม่มีปุ่มส่งออก และไม่มีคำว่า "ผู้ดูแลระบบ"
- ยอดเทียบเป้า: `.bigstat` + `UI.meter({ mode: 'target', mark: UI.monthPace().pct })` (ขีด = เดือนผ่านไปกี่ %) · คาดการณ์สิ้นเดือน = ยอดถึงตอนนี้ ÷ เวลาที่ผ่านไป × ทั้งเดือน (ต้นเดือนยังไม่ตัดสิน ตกลงจำนวนวันขั้นต่ำกับ user)
- เทียบ "ช่วงวันเดียวกัน" ของเดือนก่อน (`UI.monthPace().prevSame`) ไม่ใช่ทั้งเดือนก่อน · สาขา/ช่องทาง: `UI.rankList` แบบมี `prev` (ยอด + โตเท่าไรในแถวเดียว)
- แนวโน้ม: `UI.lineChart` ยอดสะสมรายวันเทียบเส้นเป้าสะสม (dashed) หรือ `UI.barChart` รายสัปดาห์ที่ช่วงล่าสุด `dim` · เงินแสดงเป็น "ล้าน" (`UI.fmtMillion`) ไม่ใช่ "5.6M"
- ข้อมูลเป็นแถวคำสั่งซื้อ (CSV) ได้: โหลดด้วย `UI.getCSV` แล้วรวมเองด้วยวันไทย (`UI.dayKey`) หรือให้หลังบ้านรวมมาเป็น JSON

## ข้อมูลที่ไม่เข้าสูตรไหน
ไล่ brief ทีละข้อ แล้วเลือกทาง (SKILL.md): ถ้าคนดูต้องไล่แถวด้วยตัวกรองช่วง/ตาราง/ส่งออก ใช้ ENGINE และเลือก section จาก `layout.md` · ถ้าต้องการคำตอบจากสถานะสดหรือหลายแหล่ง ใช้หน้าออกแบบเอง และเลือกชิ้นส่วนจาก `design.md`
